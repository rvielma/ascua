01 · el diff que sobra

Reconstruir el árbol para ver qué cambió

Con Virtual DOM, cambiar un número reconstruye una representación del árbol y la compara con la anterior. El trabajo depende del tamaño del árbol, no del cambio.

Ascua ata el dato a su nodo una vez, al compilar. Cambiarlo ejecuta la escritura que le toca. Nada que deducir, porque nada se olvidó.

Pulsa y mira el registro: cada click es un setText sobre el mismo nodo, que nunca se sustituye.

02 · el núcleo

signal, effect, memo

Un signal guarda un valor. Un effect ejecuta código y anota qué signals leyó; si alguno cambia, vuelve a correr. Un memo guarda su resultado y se calla si no cambió. 

const count = signal(0);
const doble = memo(() => count() * 2);

effect(() => console.log("doble =", doble()));

count.set(21);   // imprime "doble = 42"
count.set(21);   // silencio: el memo no cambió

Nadie declara dependencias. Se descubren al leer.

Escribir en un signal no ejecuta nada: marca. Los efectos se encolan y corren cuando la marca terminó de propagarse, así que un grafo en diamante no deja ver valores a medias y una rama que no cambió no recalcula.

03 · plantillas

Una closure es reactiva; lo demás, no

La plantilla es HTML: class y onclick, no className ni onClick. Se copia y se pega desde cualquier sitio.

escribes

view`
  <button
    onclick=${() => count.update(c => c + 1)}
  >
    Clicks: ${() => count()}
  </button>`

sale

const _n0 = _$el("button");
_$on(_n0, "click",
  () => count.update(c => c + 1));
const _n1 = _$txt("Clicks: ");
_$add(_n0, _n1);
const _n2 = _$dtxt(() => count());
_$add(_n0, _n2);

El efecto tiene _n2 capturado. Ya sabe a qué nodo escribir.

${count()} pone el valor y se olvida. ${() => count()} crea un efecto. La diferencia es sintáctica: se ve en la plantilla, sin mirar tipos.

04 · composición

Componentes y control de flujo

Minúscula es HTML, mayúscula es componente. Un componente recibe props y devuelve un nodo: <Ficha titulo=${t}/> compila a Ficha({ titulo: t }), que puedes escribir a mano. Sin clase base ni ciclo de vida. 

view`
  <main>
    <Show when=${() => sesion() !== null}>
      <Ficha titulo=${() => sesion()!.nombre}>
        <ul>
          <For each=${() => tareas()}
               key=${(t) => t.id}
               render=${(t) => view`<li>${t.titulo}</li>`}/>
        </ul>
      </Ficha>
      <Else><Acceso onentrar=${entrar}/></Else>
    </Show>
  </main>`

Los hijos son una receta que recibe el padre, no nodos ya hechos.

Cada rama de <Show> se construye dentro de su propia función, así que la que no se ve todavía no existe. Al cambiar la condición se libera el scope entero de la anterior: efectos, memos, listeners y onCleanup.

Entra, marca una tarea, añade otra y sal. El contador de abajo lo lleva: una construcción por clave, y todas liberadas al salir. Marcar no rehace la fila, escribe en un atributo y en un texto.

El campo usa prop:value. El atributo value de un <input> solo fija el valor inicial y deja de mandar en cuanto alguien teclea; la propiedad manda siempre. De eso depende poder vaciar un formulario desde el código.

05 · listas

La única reconciliación que queda

En texto y atributos no hay nada que comparar. En una lista sí: hace falta saber qué le pasó a cada elemento. Se comparan claves, no árboles, y solo cuando la lista cambia.

El color se fija al construir cada item. Rota o invierte: los colores viajan con sus items porque son los mismos nodos, movidos. Eso es lo que conserva el foco, el scroll y lo que hubiera a medio escribir.

06 · estilos

El CSS se queda en el compilador

Un <style> dentro de una plantilla no deja nada en tiempo de ejecución: ni etiqueta inyectada, ni insertRule. Al compilar se deriva un identificador del contenido y se reescribe cada selector.

en la plantilla

<style>
  .caja { border: 1px solid; }
  p:hover { opacity: .5; }
</style>

en el .css del build

.caja[data-ascua-98909ba2] {
  border: 1px solid;
}
p[data-ascua-98909ba2]:hover {
  opacity: .5;
}

El atributo va antes de la pseudo-clase, no al final.

El scope es por plantilla. El CSS de un componente no se filtra a los componentes que use dentro, que es justo lo que se espera de un scope, y por eso cada uno lleva sus estilos consigo.

07 · webassembly

Un artefacto, no veinte

01

81 KB para todo

El mismo .wasm en Node, Bun, Deno y el navegador. SWC publica una decena de binarios por plataforma; esbuild, veinte.

02

Sin postinstall

Nada que descargar al instalar, que es el agujero que stil existe para cerrar. Un artefacto que auditar, no diez.

03

Corre en tu pestaña

El playground es el compilador entero, sin servidor detrás. Escribe y mira lo que sale.

04

Y no baja al cliente

En el navegador el DOM vive en JavaScript: cruzar la frontera cuesta más que la operación. Por eso el runtime son 1,77 kB de JS.

09 · empezar

Dos comandos y un plugin

stil add @ascua/runtime
stil add -D @ascua/vite-plugin

Y si la aplicación tiene más de una pantalla, stil add @ascua/router: 0,98 kB en los que la ruta es un signal más, con parámetros (/pedidos/:id), enlaces que no recargan y vistas que se liberan al salir de ellas. 

// vite.config.ts
import ascua from "@ascua/vite-plugin";

export default { plugins: [ascua()] };

El compilador viene dentro del plugin. No hay binario que instalar.

A partir de ahí es Vite. Salen un .js y un .css que se publican en cualquier hosting estático — este sitio, sin ir más lejos.
