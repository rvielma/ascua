Ascua reactividad templates componentes estilos compilador playground v0.1.0

Escribes HTML y TypeScript. El compilador es WebAssembly.

Sin Virtual DOM: cada dato conoce el nodo que le corresponde, así que un cambio de estado ejecuta la operación de DOM que toca y ninguna más.

2,18 kB una aplicación entera, gzip 1,77 kB el runtime 0 dependencias 173 tests

01El trabajo que nadie tenía que hacer

Un framework con Virtual DOM responde a un cambio de estado reconstruyendo una representación del árbol y comparándola con la anterior para deducir qué tocar. El trabajo es proporcional al tamaño del árbol, no al del cambio.

Ascua establece la relación entre un dato y su nodo una sola vez, al compilar la plantilla. A partir de ahí, cambiar el dato ejecuta la operación que le corresponde. No hay nada que deducir porque nada se olvidó.

Pulsa. Cada click produce una escritura sobre un nodo de texto que nunca se sustituye: ni un árbol recorrido, ni una comparación.

02Tres primitivas, y ninguna más

Un signal guarda un valor. Un effect ejecuta código y observa qué signals lee mientras lo hace; cuando uno cambia, ese efecto —y solo ese— se reejecuta. Un memo es un efecto que guarda lo que devuelve y no se lo pasa a nadie si no cambió. 

const count = signal(0);
const doble = memo(() => count() * 2);

effect(() => console.log("doble =", doble()));

count.set(21);   // imprime "doble = 42"
count.set(21);   // no imprime nada: el memo no cambió

Nadie declaró las dependencias: se descubren al leer.

Marcar es barato y recalcular no, así que escribir en un signal no ejecuta nada: solo marca. Los efectos afectados se encolan y corren cuando la marca ha terminado de propagarse. Eso es lo que evita leer un valor intermedio inconsistente en un grafo en diamante, y lo que impide recalcular ramas cuyo valor no cambió.

03Una closure es reactiva; lo demás, no

La plantilla es HTML de verdad: class y onclick, no className ni onClick. Marcado que se puede copiar y pegar.

lo que escribes

view`
  <button
    onclick=${() => count.update(c => c + 1)}
  >
    Clicks: ${() => count()}
  </button>`

lo que genera

const _n0 = _$el("button");
_$on(_n0, "click",
  () => count.update(c => c + 1));
const _n1 = _$txt("Clicks: ");
_$add(_n0, _n1);
const _n2 = _$dtxt(() => count());
_$add(_n0, _n2);

El efecto captura _n2: ya sabe qué nodo tocar.

La distinción es sintáctica, no de tipos: ${count()} inserta el valor y no vuelve a mirarlo; ${() => count()} crea un efecto. Mirando la plantilla se sabe qué puede cambiar, sin conocer los tipos ni confiar en ninguna regla implícita.

04Componentes, y el control de flujo

La inicial decide: minúscula es HTML, mayúscula es componente. Un componente es una función que recibe props y devuelve un nodo, y eso es todo lo que es: <Ficha titulo=${t}/> compila a Ficha({ titulo: t }), que se puede escribir a mano. No hay clase base, ni ciclo de vida, ni nada que registrar. 

view`
  <main>
    <Show when=${() => sesion() !== null}>
      <Ficha titulo=${() => sesion()!.nombre}>
        <ul>
          <For each=${() => tareas()}
               key=${(t) => t.id}
               render=${(t) => view`<li>${t.titulo}</li>`}/>
        </ul>
      </Ficha>
      <Else><Acceso onentrar=${entrar}/></Else>
    </Show>
  </main>`

Los hijos son una receta que recibe el padre, no nodos ya hechos.

<Show> construye cada rama dentro de su función: la que no se ve no existe todavía, ni sus nodos ni sus efectos. Al cambiar la condición, el scope de la rama anterior se libera entero —efectos, memos, listeners, onCleanup— y se construye la otra. Si la condición devuelve el mismo valor que ya tenía, no se toca el DOM.

Entra, marca alguna tarea, añade otra y sal. El contador de abajo lleva la cuenta: las filas se construyen una vez por clave, y al salir se liberan todas. Marcar una tarea no reconstruye su fila — escribe en un atributo y en un nodo de texto.

Un formulario necesita una cosa más: prop:value. El atributo value de un <input> es su valor inicial y deja de mandar en cuanto el usuario teclea; la propiedad manda siempre. Es la diferencia entre poder vaciar un formulario desde el código y no poder.

05El único sitio con reconciliación

Para texto y atributos no hay nada que comparar. Con una lista dinámica sí: no se puede saber de antemano qué le pasó a cada elemento. La diferencia con un VDOM es el alcance — esto compara una lista de claves, no un árbol, y solo cuando esa lista cambia.

Cada item recibe su color al construirse. Rota o invierte: los colores viajan con sus items porque son los mismos nodos, movidos. Eso es lo que conserva el foco, el scroll y lo que el usuario estuviera escribiendo.

06Los estilos se quedan en el compilador

Un bloque <style> dentro de una plantilla no deja nada en tiempo de ejecución: ni <style> inyectado, ni insertRule, ni runtime de estilos. Al compilar se calcula un identificador a partir del contenido y se reescribe cada selector para que solo case con los elementos de esa plantilla.

en la plantilla

<style>
  .caja { border: 1px solid; }
  p:hover { opacity: .5; }
</style>

en el .css del build

.caja[data-ascua-98909ba2] {
  border: 1px solid;
}
p[data-ascua-98909ba2]:hover {
  opacity: .5;
}

El atributo va antes de la pseudo-clase, no al final.

El scope es por plantilla, así que el CSS de un componente no se filtra a los componentes que use dentro. Eso es lo que se espera de un scope, y es la razón de que cada componente lleve sus propios estilos.

07El compilador es WebAssembly

Un solo artefacto de 81 KB que corre en Node, Bun, Deno y en el navegador. SWC publica una decena de binarios por plataforma; esbuild, veinte. Ascua publica uno.

Sin postinstall que descargue un binario —el vector que stil existe para cerrar— y sin diez artefactos que auditar. Y va igual de rápido que el nativo, porque se ahorra un proceso por archivo.

Corre en tu pestaña: abre el playground y mira lo que genera mientras escribes.

En el navegador, en cambio, WebAssembly no aporta: el DOM vive en JavaScript y cada cruce de la frontera cuesta más que la operación. Por eso el runtime que llega al usuario son 1,77 kB de JavaScript, y el WebAssembly se queda donde sí gana.

09Empezar

stil add @ascua/runtime
stil add -D @ascua/vite-plugin
// vite.config.ts
import ascua from "@ascua/vite-plugin";

export default { plugins: [ascua()] };

Sin binarios que instalar: el compilador es el .wasm del paquete.

El resto es Vite. El resultado son un .js y un .css que se despliegan en cualquier hosting estático.
